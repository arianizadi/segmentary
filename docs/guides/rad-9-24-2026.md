# rad_9_24_2026: two comparable training arms

`rad_9_24_2026` is a flat delivery of 314 rail images (305 PNG, 9 JPG, stems
`0000`-`0313`) with Supervisely polygon JSONs (`jsons/`), the annotator's own
rendered masks (`masks_machine/`) and side-by-side previews. 292 of the images
are byte-identical to `paul-test-rtis` v2 (205 train / 37 val / 50 test); the
15 disputed `no_anomalies_0251..0265` train images are absent; 22 images are new
(`0174`-`0184`, `0250`, `0251`, `0253`-`0261`). For 290 of the 292 shared images
the repository render of the new JSON is pixel-identical to the v1/v2 mask; the
two exceptions are train images `0249` and `0252`, edited in April 2026.

The class ids are the existing `paul-test-rtis` label space (21 classes,
`mud-pumping` = 13, ignore 255). `obj_class_to_machine_color.json` in the
delivery is 1-based and must not be used as an id map.

## Detected label defects in `masks_machine/`

`masks_machine` is produced from the JSONs by the annotator's own script, which
starts from a black canvas and draws exterior rings only. Compared with the
repository render (`scripts/prepare_rtis.render`: cv2.fillPoly in saved order,
holes cut out, void and uncovered pixels = 255), over all 314 images:

| Quantity | Pixels |
| --- | ---: |
| Covered by no polygon (255 in the repository render) | 210,762 |
| Of those, labelled 0 = person in `masks_machine` | 210,762 |
| Changed by ignoring the 165 polygon holes (mostly pole/fence over sky and terrain) | 299,121 |
| Total disagreement between `masks_machine` and the repository render | 1,478,606 (0.20%) |
| Person pixels, repository render / `masks_machine` | 907,504 / 1,125,758 |

The remaining disagreement is boundary rasterisation (Pillow fills fewer edge
pixels than cv2). 60 images contain class 0 without any person polygon.
`scripts/prepare_rad.py` writes these numbers per image and in total to
`audit/label-audit.json` and `audit/label-audit.csv` in every prepared dataset.
It records; it never corrects.

## The two arms

| Dataset | Labels | Split | Role |
| --- | --- | --- | --- |
| `rad_9_24_2026-paul` | `masks_machine` byte copies | stratified random, seed 0 | exactly the delivered request |
| `rad_9_24_2026-fixed-grouped` | re-rendered from `jsons/` | scene-grouped, carried over from v2 | the split policy (and the label fix) |

The two arms differ in both labels and split. A third arm with the re-rendered labels on the
stratified split, isolating the label fix, was stopped on 2026-10-05 at 8 of 40 jobs: over 8
matched eomt runs the label fix changed cab-view mud IoU (pixels pooled) on stratified val by -3.3 to +4.7
points, -0.1 on average, so the GPUs went to the split comparison. The stratified split spec (step 2 below)
is still needed: the `paul` arm uses it.

Both reuse taxonomy space `paul-test-rtis`, mapping `paul-test-rtis` and stage
name `rtis` (`configs/datasets/rad_9_24_2026-*.yaml`). Only the grouped arm sets
`require_groups: true`; its `splits.json` carries `groups`. The stratified `paul` arm
deliberately carries no `groups` map because scene groups do cross splits there.

## Commands

```bash
cd segmentary
export RAD=/path/to/rad_9_24_2026           # img/, jsons/, masks_machine/
export OUT=/path/to/prepared                # new directory tree

# 1. Scene-grouped split: carry v1/v2 membership over by image sha256, new images from YAML.
PYTHONPATH=.:src python scripts/make_rad_splits.py grouped \
  --source $RAD --reference data/paul-test-rtis \
  --new-images configs/datasets/rad_9_24_2026-new-image-groups.yaml \
  --out $OUT/specs/grouped.json                      # train 217 / val 37 / test 60

# 2. Stratified random split for the paul arm (group names from step 1: directory layout only).
PYTHONPATH=.:src python scripts/make_rad_splits.py stratified \
  --source $RAD --group-spec $OUT/specs/grouped.json --seed 0 --sizes 227,37,50 \
  --rare-threshold 50 --anomaly-classes mud-pumping,standing-water,vegetation-overgrowth \
  --out $OUT/specs/stratified.json                   # train 227 / val 37 / test 50

# 3. The two datasets. --reference-samples proves render parity with v1/v2.
for arm in paul:stratified:paul fixed-grouped:grouped:rendered; do
  IFS=: read name spec labels <<< "$arm"
  PYTHONPATH=.:src python scripts/prepare_rad.py --source $RAD \
    --split-spec $OUT/specs/$spec.json --labels $labels \
    --name rad_9_24_2026-$name --target $OUT/rad_9_24_2026-$name \
    --reference-samples data/paul-test-rtis/audit/samples.json
done
```

`prepare_rad.py` stages into `<target>.preparing`, refuses an existing target,
re-hashes every written image and decoded mask, checks that nothing else exists
under `images/` or `masks/`, and writes `audit/validation.json`. With
`--reference-samples` it compares the sha256 of the repository render for every
image that is also in the reference and fails unless the only mismatches are
`0249` and `0252` (identified by image sha256 in `prepare_rad.KNOWN_EDITED`).
Expected: 290 matches, 2 known edits, 22 new images. The reference may be v1
(307 samples) or v2 (292): both give the same split because the 15 extra v1
images are absent from the delivery.

The layout is the one the RTIS campaign runtime verifies: `images/<split>/<group>/<stem>.<ext>`
(original bytes), `masks/<split>/<group>/<stem>.png` (mode L), `splits.json`,
`audit/samples.json` with `key, split, image_extension, width, height, image_sha256,
mask_sha256`, plus `classes.json`, `README.md`, `audit/split-spec.json`,
`audit/label-audit.*` and `audit/validation.json`.

## The stratified rule and its one deviation

Stratification labels per image are the presence (from JSON `classTitle`) of
each anomaly class (`mud-pumping`, `standing-water`, `vegetation-overgrowth`) and of
every other class that appears in fewer than 50 images, computed from the data
with `void` excluded. "Present" means at least one JSON object of that class,
not a painted pixel in the rendered mask (recorded as `method.presence_rule` in
the spec). On this delivery that adds `person` (35), `truck` (43) and
`on-rails` (46); `tram-track` has 51 JSON images (as does `rail-embedded`) and is
therefore not rare under the rule even though it paints only 49 masks, two of its
polygons being fully overdrawn by later objects. Counted by painted pixels it
would be rare; its 36/5/10 split is proportional anyway. The split is multi-label iterative
stratification (Sechidis, Tsoumakas and Vlahavas, 2011): the rarest remaining
label is placed first, each image goes to the split that most wants that label,
ties fall to the split with the most free capacity and then to a seeded RNG.
Sizes are exact (227/37/50). The tool fails if any stratification label with at
least three images is missing from any split.

Deviation: the 11 images with `min(width, height) < 1024` are pinned to train
before stratification. Every val/test image of v1/v2 was at least 1024 px on
both sides, so the whole-image evaluation path on smaller inputs has never been
exercised by the 36 campaign models. Pinning keeps evaluation on the tested path;
it is an operational choice, not part of the requested rule, and is recorded in
`method.pinned_small_images_to_train` of the spec.

Leakage caveat: the stratified split is random over frames. Of the 22 scene
groups, 17 have frames in more than one split, including the ten test frames of
`sunny-mountain-cab-view` whose siblings land in train. Val and test numbers from
the stratified `paul` arm therefore measure same-recording generalisation, not
new-recording generalisation, and are not comparable with v1/v2 history. The
`_grouping_status` string in `splits.json` says so.

## Grouped split decisions for the 22 new images

`configs/datasets/rad_9_24_2026-new-image-groups.yaml` is keyed by image sha256
and carries the stem only as a checked annotation. The evidence is visual only
(cab cowl, `Vmax` overlay, pig watermark, scenery); recording provenance has not
been confirmed, hence `provisional_until_recording_provenance_confirmed`.

| Images | Group | Split | Reason |
| --- | --- | --- | --- |
| `0251`, `0253`-`0261` | `sunny-mountain-cab-view` | test | cab cowl + Vmax overlay + alpine scenery, the signature of the ten held-out test frames `0114`-`0123` |
| `0250` | `sunny-mountain-stations` | train | urban terminus, no cowl, sort neighbour of train `0252` |
| `0174` | `green-roadside-cab-view` | train | pig watermark seen only in that train group |
| `0179`-`0182`, `0184` | `sunny-mainline-cab-view` | train | Vmax overlay without cowl, a train-only signature |
| `0175`-`0178`, `0183` | `new-unmatched-2026` | train | no marker shared with any val/test image |

Result: train 217 / val 37 / test 60. Val membership is identical to v1/v2 and
test is a superset of the v2 test set, so the grouped arm keeps val history
comparable. Train image `0252` carries the same cowl as the new test block and
was already in v1/v2 train; that pre-existing leak is documented, not fixed.

## Viewpoint subsets and the comparison report

`configs/datasets/rad_9_24_2026-viewpoints.yaml` labels every image (keyed by image sha256)
`cab-view` (228), `track-level` (75) or `other` (11) from visual judgement only: two labelling
passes by AI model subagents with adjudication of disagreements (the same model, so not
independent annotators). `cab-view` is the deployment-relevant subset. On the grouped val split
all 17 cab-view images with mud come from `rural-overcast-cab-view`, a forward view from a camera
mounted visibly lower than a locomotive cab. Val numbers come from the checkpoint selected (and
early stopped) on `val_iou/mud-pumping` of the same val split, from one seed, so they are
optimistic and carry no uncertainty estimate.

### Metrics

Every published RAD 9/24 number counts a class only on the images that contain it
(`segmentary.engine.present_image`, shared by `scripts/rad_subset_metrics.py`,
`scripts/rad_report.py`, `scripts/cv_report.py` and the publisher). An image is present for a
class when its ground-truth mask has at least one pixel of it (255 ignored), the same rule as
`presence_rule` in `configs/datasets/rad_9_24_2026-cv-spec.json`. For a set of images (a
viewpoint subset, a split, or the pooled out-of-fold images of cross-validation):

- **Mud-pumping IoU** = mean over the images with mud-pumping of the per-image IoU
  TP/(TP+FP+FN), from each image's own confusion matrix. Images without mud-pumping are left
  out, so mud predicted on clean track does not lower it; a mud image where nothing is predicted
  scores 0.
- **Mud precision and recall** = TP/(TP+FP) and TP/(TP+FN), with TP, FP and FN summed over the
  images with mud-pumping only.
- **Per-class IoU** = the same present-image IoU for every class, shown as `—` (not 0) for a
  class no image of the set contains. The per-split, model and cross-validation pages have a
  per-class table; the CSVs have `iou_present_images:<class>` and `images_present:<class>`.
- **mIoU** = mean of the per-class IoU over the classes present in at least one image of the
  set.

Next to the metrics the study tables show inference cost from each run's performance record
(model-only forward passes, batch 1, 1024x1024, BF16): speed (FPS), GPU memory and parameters
(millions). GPU memory is the whole-process total including the CUDA context
(`measurements.process_total_bytes`) when the record has it, else PyTorch's allocator peak
reserved bytes (`measurements.peak_reserved_bytes`), marked `†` because it excludes the CUDA
context (driver overhead, a few hundred MB). Cross-validation shows the mean FPS and the largest
memory over a model's fold records.

`n` beside a metric is the number of images with mud-pumping behind it. The earlier pixel-pooled
metrics (one confusion matrix summed over the set, where a few images with large mud areas
decide mud IoU: on the stratified val split 5 track-level `trackside-maintenance` close-ups,
0071, 0076, 0081, 0089 and 0091, hold about 95% of the mud pixels) stay in `rad-comparison.csv`
and `cv-report.csv` as `*_pixel_pooled` columns, and in the per-run tables of the published arm
and model pages. Training is unchanged: the `paul` and `fixed-grouped` checkpoints were still
selected on the pixel-pooled `val_iou/mud-pumping`.

```bash
# one run: per-image confusions + reported total + arm samples -> subset metrics (val or train);
# --checkpoint final for final-auto-val confusions of a primary_checkpoint: final campaign
PYTHONPATH=.:src python scripts/rad_subset_metrics.py --confusion <per-image-confusion.json.gz> \
  --total <state/job.json | results-val.json> --samples <arm>/audit/samples.json \
  --viewpoints configs/datasets/rad_9_24_2026-viewpoints.yaml
# all completed campaign jobs and scored fork runs (validation only) -> README.md + CSV
PYTHONPATH=.:src python scripts/rad_report.py --out <dir outside the campaign roots>
```

`rad_report.py` scores each campaign at its primary checkpoint: `best-auto-val` (selected on
validation, the `paul` and `fixed-grouped` r2 campaigns) unless `campaign.json` records
`primary_checkpoint: final`, whose result is `final-auto-val`, accepted only when the job trained
the whole `target_steps` budget (as `scripts/cv_report.py` does). The CSV's `checkpoint` column
and the README's headline say which; the "selected on validation" caveat names only the
best-checkpoint arms.

## Scene-grouped split, every catalog model

`configs/campaigns/rad_9_24_2026-fixed-grouped-all.yaml` reruns the scene-grouped split with every
catalog model (36 models x 4 starting points, plus BiSeNetV1/V2, ESPNet and DenseASPP-121/161
from their recipe weights only: 149 jobs, seed 0) and `primary_checkpoint: final`: no early
stopping, every job trains the full 4,000 steps and the final checkpoint is the result, so
nothing is selected on the validation images. On HDRFS it is `fgall-seed0-20261007` (smoke
`fgall-smoke-20261007`, frozen checkout `/data/izadia1/projects/segmentary-rad-fgall-fce0ea0a`).
The earlier 10-model best-checkpoint run, `fixed-grouped-seed0-20261005-r2`, stays as it is.

## Stratified group cross-validation

The single grouped split is honest but noisy (its 3 val groups hold one mud-pumping cab-view
scene), and the stratified split leaks frames of one scene across train and val. The
`rad_9_24_2026-cv` campaign (`configs/campaigns/rad_9_24_2026-cv.yaml`) runs a 5-fold stratified
group CV over the fixed-grouped arm's 254 train+val images, keeps its 60 test images out of every
fold, trains every job for the full budget and scores the final checkpoint, and reports pooled
out-of-fold metrics. Fold table, launch commands and cost:
[cross-validation guide](cross-validation.md#worked-example-rad_9_24_2026).

## Publishing the results

`scripts/publish_rad_results.py` re-renders `docs/results/rad_9_24_2026/` every three hours from
the HDRFS records (read-only) and pushes it from a separate publisher clone: a short study page
(`README.md`: what was tested, the key result, one compact table per split, Paul's paper model,
caveats), `details.md` with the full record (label defects, comparison tables, fork runs,
provenance), one directory per split, and with `--cv-campaign` the cross-validation report in
`cross-validation/` (`README.md` + `cv-report.csv`, rendered in-process by
`scripts/cv_report.py` with the `--viewpoints` subsets). Every page leads with the metrics
above; "best starting point" is chosen by the train-camera (`cab-view`) mud-pumping IoU. A
partial CV campaign is published
with its coverage (unfinished models marked `*`). When the CV campaign is missing or its report
fails, the previously published `cross-validation/` pages are kept, the study page says so, the
error is recorded as `cv_error` in `publisher-status.json` and the next cycle retries.

Each split is scored at its campaign's primary checkpoint (above). Several `--campaign` roots may
share a split: the newest (`created_at`) with a completed job is the split's pages and its study
table, so `fgall-seed0-20261007` becomes the "Scene-grouped split" with its first finished run
and until then the r2 campaign keeps the page filled, with a line giving the new run's coverage
("0 of 149 runs done"). A superseded campaign keeps no arm pages; `details.md` summarises it
("First scene-grouped run (10 models, best-on-validation checkpoint)") with its CSV in
`earlier-runs/`. A partial split is published with its coverage (models with unfinished
starting points marked `*`), a model planned from one starting point only is labelled so, and a
final-checkpoint split carries no "selected on validation" caveat (Paul's split keeps it).

Deploy from a frozen code snapshot (`$CODE`, with a `SNAPSHOT_COMMIT` file), never from the
publisher clone. `STOP` in the state directory ends the running loop; delete it before
starting the new one. `$PY` is the campaign environment's interpreter. The scene-grouped arm
pages take about 1.7 MB per job (67 MB for the 40 r2 jobs), so the 149-job campaign needs a larger
tree cap than the 320 MB that fits the r2 arms.

```bash
STATE=/data/izadia1/projects/segmentary-runs/rad_9_24_2026/publisher
RUNS=/data/izadia1/projects/segmentary-runs/rad_9_24_2026
touch $STATE/STOP              # wait until the old loop has exited, then:
rm $STATE/STOP
tmux new-session -d -s rad-publisher "cd $STATE && env -u HF_HOME CUDA_VISIBLE_DEVICES= \
  PYTHONPATH=$CODE:$CODE/src $PY $CODE/scripts/publish_rad_results.py \
  --checkout /data/izadia1/projects/segmentary-rad-publisher \
  --interval-seconds 10800 --max-tree-mb 450 \
  --campaign $RUNS/paul-seed0-20261005-r2 \
  --campaign $RUNS/fixed-grouped-seed0-20261005-r2 \
  --campaign $RUNS/fgall-seed0-20261007 \
  --cv-campaign $RUNS/cv-seed0-20261006 \
  --viewpoints $CODE/configs/datasets/rad_9_24_2026-viewpoints.yaml >> publisher.log 2>&1"
```

The loop's first cycle runs one interval after the last attempt recorded in
`publisher-status.json`.
